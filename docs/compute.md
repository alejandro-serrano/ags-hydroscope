# Compute budget

How long do the planned runs take on the target machine (Apple M2 Pro, MPS, fp32)? Before the
real runs, `scripts/benchmark_steps.py` times a few steps of each of the 8 run configs and
extrapolates. The table below is written by that script; do not edit it by hand.

## What is measured

- Training: `run_epoch` from `hydroscope.training.train`, unchanged, with the real loaders
  (num_workers 2, augmentation, per-band normalization, resize to 224 on the device), micro-batch
  32 and accumulation 2 (optimizer batch 64). The first 5 optimizer steps are a warm-up and are
  not timed; the timed part runs up to step 100. The result is seconds per optimizer step.
- Validation: 20 batches of 32 in eval mode without gradients, after one untimed warm batch.
- Peak memory: `PeakMemoryTracker` (MPS driver memory), sampled after each step.
- Estimate: one epoch is ceil(16200 / 64) optimizer steps plus ceil(5400 / 32) validation batches.
  A run is 15 epochs plus the final validation predict and the 5400-patch `eurosat_test` predict
  at the validation rate.

## Caveats

- The hours per run are an upper bound: early stopping (patience 3) may end a run before epoch 15.
- Thermal throttling over a run of hours can make the real time longer than a short benchmark.
- Peak memory is approximate: MPS driver memory is process-wide and may keep memory freed by the
  previous config, so later configs can show leftovers.
- The timed call restarts the data loader iterator after the warm-up call, so a small prefetch
  refill is included in the time.
- num_workers is 2 for every model (protocol); a slow loader would show up in every row equally.
- Everything is fp32 with no autocast.
